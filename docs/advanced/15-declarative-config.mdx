---

Every resource (OUs, user types, apps, flows, roles, connections, themes and so on) can be written as YAML with a `resource_type`. That makes configuration reviewable, versionable and repeatable across environments.

There are three ways YAML gets into a server.

| Way | What happens | Editable afterwards |
| --- | --- | --- |
| `POST /import` | The resources are created or updated in the database | Yes, like anything made in the console |
| Declarative files | Files in the deployment's resources directory are loaded at startup | No, read-only (`403` on writes) |
| `thunderid bootstrap` | `setup.sh` imports the default bundle (`backend/cmd/server/bootstrap/*.yaml`) before the server starts | Yes |

**Store modes:** each resource type has a store mode. `mutable` uses the database only, `declarative` uses files only, and `composite` merges both, with file-defined entries read-only. The global `declarative_resources.enabled` sets the default.

**Export:** `POST /export` writes chosen resources back out as YAML. Environment-specific values become references instead of literals:

- `var:` references an ordinary value, such as a client ID, read back as it is <V2 />
- `sec:` references a secret, such as a client secret, never read back <V2 />

Variables and secrets are stored on the target server (`/variables`, `/secrets`) and resolved at import. A secret never travels in the YAML.
