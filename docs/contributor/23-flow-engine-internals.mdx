## The idea

You've built flows in the console. This module opens the engine that runs them, so you can debug a flow and extend it with your own executor.

The flow engine lives in `backend/internal/flow/`: `mgt` (flow CRUD, validation, versions), `flowexec` (the engine and `POST /flow/execute`), `core` (node implementations), `executor` (the built-in executors), `executormeta` (the executor catalogue) and `interceptor`.

## One request through the engine

1. The service resolves the flow graph, or loads the stored context for a running flow. On the first request it picks the app's flow for the flow type. For sign-in only, it falls back to the server default when the configured flow can't be found. Other flow types return a server error.
2. The engine runs the `PRE_REQUEST` interceptors. The challenge token interceptor checks the incoming `challengeToken` against a stored hash.
3. For each node: `PRE_NODE` interceptors, `Execute`, `POST_NODE` interceptors. It follows `nextNode` until a node pauses (a `PROMPT` waiting for input, or an executor returning incomplete) or the graph ends. A node that runs more than 10 times in one request is an error.
4. `POST_REQUEST` interceptors run, and the challenge token is rotated.
5. The execution context is AES-GCM encrypted and written to the runtime store with a TTL. It's deleted when the flow completes. A flow that ends on an `ERROR` step keeps its context until the TTL runs out.

The TTL is fixed when the flow starts: 3600 s for sign-in and registration, 1800 s for recovery and sign-out, 86400 s for onboarding and invitation, overridable per type in the `flow` server configuration (Ex: `authFlow.expirySeconds`, `registrationFlow.expirySeconds`). A late `executionId` gets `FES-1004`. This execution context isn't the SSO session, which is separate and per flow.

**System flows:** services run `SYSTEM` flows in process through `ExecuteSystemFlow`. Their definitions are JSON under `flow/mgt/system/` (Ex: `entity_delete_pre.json`, `revocation_post.json`).

## Adding an executor

An executor implements `providers.Executor` (`backend/pkg/thunderidengine/providers/interface.go`).

1. Build its base with `flowFactory.CreateExecutor(name, type, defaultInputs, prereqs, &ExecutorMeta{})`. The `ExecutorMeta` holds its modes, the flow types it's allowed in and its properties. `credentials_auth_executor.go` is a good model.
2. Add the name to `executormeta/constants.go`.
3. Mirror the same metadata in `executormeta/catalog.go`. `executor/catalog_parity_test.go` fails if the catalogue and the executor disagree.
4. Register it in `newBuiltInExecutorRegistrars` in `executor/register.go`.

A deployment can enable a subset of executors with the `flow.executors` config. Executors never call user or agent services directly to write. They go through the user and agent management providers ([module 22](/docs/next/contributor/providers)).

## Recap

- Each request runs interceptors, then nodes, until a node pauses or the graph ends.
- Execution state is encrypted and stored with a TTL fixed at the start.
- A new executor needs a constant, catalogue metadata and a registrar.
