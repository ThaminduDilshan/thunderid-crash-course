## The idea

ThunderID is one Go codebase that builds two binaries, plus four React apps. Before you change anything, it helps to know where each piece lives and how a request travels through a package.

## Repository map

| Path | What's there |
| --- | --- |
| `backend/cmd/server` | The data plane binary: `main.go`, `servicemanager.go` (wires every package), `bootstrap/` (the default resource bundle) |
| `backend/cmd/cpserver` | The control plane binary |
| `backend/internal/<domain>` | One package per domain: `application`, `user`, `agent`, `ou`, `role`, `flow`, `oauth`, `authn` and so on |
| `backend/internal/system` | Shared plumbing: config, database, cache, JOSE/JWT, security, logging, i18n, import/export |
| `backend/pkg/thunderidengine` | The public, embeddable engine and its `providers` interfaces |
| `backend/dbscripts` | Schema for each database, SQLite and PostgreSQL |
| `api/*.yaml` | OpenAPI specs, one per area |
| `frontend/apps` | `gate`, `console`, `admin-console`, `console-cp` |
| `frontend/packages` | Shared UI, hooks, i18n and the flow and application builders |
| `tests/integration`, `tests/e2e` | Go integration tests against a running server, Playwright end-to-end tests |
| `docs/` | The documentation site. `docs-internals/` holds specs and threat models. |

## Inside a domain package

Each package is `handler → service → store`, wired once in `init.go` by `Initialize`. `servicemanager.go` calls every `Initialize` and passes in dependencies. A package never builds its own. Files follow a fixed layout: `service.go`, `handler.go`, `store.go`, `model.go`, `constants.go`, `error_constants.go`, `store_constants.go`, `init.go`. Stores are usually wrapped in a cache-backed store.

## Four databases

| Database | Holds |
| --- | --- |
| `configdb` | Configuration: applications, flows, IdPs, roles, themes, server config. On 2.0 also variables, secrets, gateways and configuration versions. |
| `entitydb` | Identities: OUs, entities (users, agents, apps), groups, identifiers. On 2.0 also projects. |
| `runtime_transient` | Short-lived state: flow executions, authorization codes, PAR, CIBA and device requests. Can be Redis. |
| `runtime_persistent` | Longer-lived runtime data: sessions, consent, revoked tokens. |

Each can be SQLite (the default) or PostgreSQL. The cache is in memory by default, or Redis. In memory means per node, so mutable state cached there diverges across nodes.

## The embeddable engine

`backend/pkg/thunderidengine` lets another Go program embed flow execution and the OAuth/OIDC routes on its own HTTP mux. The embedder supplies the providers ([module 22](/docs/next/contributor/providers)). It gets no management APIs, no Gate or consoles, no SSO sessions, and none of the server's HTTP middleware. The data plane binary doesn't use it: it calls the same internal `Initialize` functions directly. Anything in `pkg/` is public API, so changing it needs care.


## Recap

- Two binaries from one codebase: the data plane and the control plane.
- Each domain package is `handler → service → store`, wired in `init.go`.
- Four databases split configuration, identities, short-lived and long-lived runtime data.
