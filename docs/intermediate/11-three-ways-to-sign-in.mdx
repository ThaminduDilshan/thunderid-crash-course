## The idea

In [module 5](/docs/next/beginner/applications) your React app sent people to ThunderID's sign-in page and got them back with a code. That's the most common way, but not the only one. A mobile app may want its own native screens. A command-line tool has no screens at all. ThunderID offers three **integration models**, and they differ in two things: who renders the screens, and who decides the order of steps.

| | Redirect-based | App-native | Direct API |
| --- | --- | --- | --- |
| How it works | The app redirects to ThunderID, which shows Gate | The app calls the Flow Execution API and draws each step itself | The app calls single-purpose `/auth/**` endpoints |
| Who renders the screens | ThunderID (Gate) | Your app | Your app |
| Who decides the steps | The flow, on the server | The flow, on the server | Your app |
| Do credentials pass through your app | No | Yes | Yes |
| What you get at the end | An authorization code, then tokens | An **assertion** JWT, exchanged for tokens with token exchange ([RFC 8693](https://datatracker.ietf.org/doc/html/rfc8693)) | An assertion JWT, exchanged the same way |
| Fits | Any app that can redirect, including SPAs | Native mobile and confidential server-side apps | CLIs, scripts, server-to-server |

Redirect-based and app-native run the **same flows** ([module 9](/docs/next/intermediate/building-journeys)), so a flow change reaches both. Gate itself is a client of the Flow Execution API: it's an app-native client that ThunderID ships for you.

:::info[🧳 In Wayfinder]

Wayfinder's web app uses **redirect-based** sign-in with authorization code + PKCE. Its code never sees a password. The flow runs on ThunderID, which returns a code the app swaps for a token carrying `booking:read booking:create booking:cancel`. If Wayfinder later ships a native iPhone app with its own screens, that app would use **app-native** sign-in against the same flows.

:::

## Rules that trip people up

- **Who may start a sign-in directly.** Browser and backend service (`m2m`) apps can never start an `AUTHENTICATION` or `SIGNOUT` flow on `/flow/execute`. Mobile apps need platform attestation (Play Integrity or App Attest), or Dev mode while testing. Full-stack, custom and MCP client apps need a `Flow-Secret` header when they qualify for one. Continuing a flow that's already running is always allowed, and registration and recovery are never restricted.
- **Every step carries a `challengeToken`.** The server rotates it on every response. Send back the latest one or the step fails.
- **Inputs are keyed by `identifier`.** Each input in a response has a `ref` and an `identifier`. When you post inputs back, use the `identifier` (Ex: `username`).
- **No back button.** A flow only moves forward.
- **The Direct API is off until you set a secret.** Calls to `/auth/**` need a `Direct-Auth-Secret` header matching `server.security.direct_auth_secret`. `setup.sh` generates one and prints it once. These endpoints have no rate limiting, so put an API gateway in front of them.

## 🧪 Lab

**App-native.** Create a `fullstack` app with no OAuth configuration and keep its Flow Secret. Then start a sign-in:

```bash
curl -sk -X POST $DP/flow/execute \
  -H 'Content-Type: application/json' -H 'Flow-Secret: <flow-secret>' \
  -d '{"applicationId":"<app-id>","flowType":"AUTHENTICATION"}'
```

The response lists the `inputs` to collect and the `actions` to choose from. Post them back with the `executionId` and the latest `challengeToken`. With the default flow that's:

```json
{"executionId":"<id>","challengeToken":"<token>","action":"action_001","inputs":{"username":"<user>","password":"<password>"}}
```

On `COMPLETE` the response carries an `assertion`. Run it again with `"verbose": true` and compare: `meta` is the component tree Gate draws.

**Direct API.**

```bash
curl -sk -X POST $DP/auth/credentials/authenticate \
  -H 'Content-Type: application/json' -H 'Direct-Auth-Secret: <secret>' \
  -d '{"identifiers":{"username":"<user>"},"credentials":{"password":"<password>"}}'
```

Decode both assertions and compare them with the ID token from [module 5](/docs/next/beginner/applications).

## Recap

- **Redirect-based:** ThunderID owns the screens and the steps. The safest default.
- **App-native:** your app owns the screens, ThunderID still owns the steps.
- **Direct API:** your app owns both. Meant for scripts and servers, behind a secret.
