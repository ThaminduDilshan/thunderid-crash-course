## The idea

The [Model Context Protocol](https://modelcontextprotocol.io) (MCP) lets AI agents call tools on MCP servers. An MCP server is an API like any other, so it needs the same thing as your booking API: tokens that say who's calling and what they may do. MCP's authorization spec uses OAuth 2.0, which means ThunderID can be the authorization server for your MCP servers and the clients that call them.

Once an agent works for a person, a second question appears: is the agent acting for itself, or for that person? The token has to say which.

:::info[🧳 In Wayfinder]

Wayfinder exposes its bookings as an MCP server at `http://localhost:8787/mcp`, with tools such as `recommend_bookings`.

- **Acting on its own:** the concierge agent gets its own token with `booking:recommend` and calls `recommend_bookings`.
- **Acting for a user:** a traveler signs in and lets the concierge work for them. The concierge's token now names the traveler as `sub` and the concierge in the `act` claim, so the booking API can tell exactly who did what.

:::

## Protecting MCP servers and registering clients

- **Protect an MCP server:** register it as a resource server whose identifier is its URL, add a permission per tool, and grant those permissions through roles. The server validates tokens offline against `/oauth2/jwks`.
- **Register MCP clients:** manually (app type `mcp`), through Dynamic Client Registration (RFC 7591, enabled with `oauth.dcr.enabled`), or from a Client ID Metadata Document.

ThunderID also runs an MCP server of its own at `/mcp`, so an AI coding assistant can manage ThunderID ([module 20](/docs/next/advanced/also-in-the-box)).

## Agents acting for users

| Pattern | How | What the token says |
| --- | --- | --- |
| Agent sign-in | The agent completes a sign-in flow (password, OTP, magic link, passkey). The app must list its agent type in `allowedAgentTypes`. | `sub` is the agent |
| **On behalf of a user** | The user signs in and consents. The agent gets a token through authorization code, CIBA, device code or token exchange. | `sub` is the user, `act` is the agent |
| **Agent to agent** | Token exchange with an `actor_token` | Nested `act` claims record the whole chain |

## Recap

- An MCP server is a **resource server**. MCP clients are **applications**.
- When an agent acts for a user, `sub` is the user and `act` is the agent.
- Agent-to-agent calls chain through token exchange, and nested `act` claims keep the history.
