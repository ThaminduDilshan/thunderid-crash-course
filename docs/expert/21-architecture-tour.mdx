## The idea

ThunderID is one Go codebase that builds two binaries, plus four React apps. It helps to know where each piece lives and how a request travels through a package.

## Repository map

| Path | What's there |
| --- | --- |
| `backend/cmd/server` | The data plane binary: `main.go`, `servicemanager.go` (wires every package), `bootstrap/` (the default resource bundle) |
| `backend/cmd/cpserver` | The control plane binary |
| `backend/internal/<domain>` | One package per domain: `application`, `user`, `agent`, `ou`, `role`, `flow`, `oauth`, `authn` and so on |
| `backend/internal/system` | Shared plumbing: config, database, cache, JOSE/JWT, security, logging, i18n, import/export |
| `backend/pkg/thunderidengine` | The public, embeddable engine and its `providers` interfaces |
| `backend/dbscripts` | Schema for each database, SQLite and PostgreSQL |
| `api/*.yaml` | OpenAPI specs, one per area |
| `frontend/apps` | `gate`, `console`, `admin-console`, `console-cp` |
| `frontend/packages` | Shared UI, hooks, i18n and the flow and application builders |
| `tests/integration`, `tests/e2e` | Go integration tests against a running server, Playwright end-to-end tests |
| `docs/` | The documentation site. `docs-internals/` holds specs and threat models. |

## Inside a domain package

Each package is `handler → service → store`, wired once in `init.go` by `Initialize`. `servicemanager.go` calls every `Initialize` and passes in dependencies. A package never builds its own. Files follow a fixed layout: `service.go`, `handler.go`, `store.go`, `model.go`, `constants.go`, `error_constants.go`, `store_constants.go`, `init.go`. A management resource's store usually comes in three modes: mutable (database), declarative (files) and composite (both), as in [module 18](/docs/next/advanced/declarative-config). Some stores also have a cache-backed wrapper ([module 23](/docs/next/expert/caching)).

## Four databases

| Database | Holds |
| --- | --- |
| `configdb` | Configuration: applications' inbound and OAuth settings, flows, IdPs, roles, themes, server config, variables, secrets, gateways and configuration versions. |
| `entitydb` | Identities: OUs, entities (users, agents and applications as `ENTITY` rows, [module 22](/docs/next/expert/entities)), groups, identifiers and projects. |
| `runtime_transient` | Short-lived state: flow executions, authorization codes, PAR, CIBA and device requests. Can be Redis. |
| `runtime_persistent` | Longer-lived runtime data: sessions, consent, revoked tokens and entity state. |

Each can be SQLite (the default) or PostgreSQL. The cache is separate ([module 23](/docs/next/expert/caching)).

## Recap

- Two binaries from one codebase: the data plane and the control plane.
- Each domain package is `handler → service → store`, wired in `init.go`.
- Four databases split configuration, identities, short-lived and long-lived runtime data.
