:::note[🎯 What you'll do]

- Run ThunderID on your laptop
- Sign in to both consoles and see a change travel from one plane to the other
- Get a token, so the later labs can call the management API

:::

## What you're about to run

The **quickstart pack** runs three ThunderID deployments that are already wired together. You met the two planes in [module 2](/docs/next/beginner/what-thunderid-is). The third one exists only to sign operators into the control plane.

| Deployment | URL | Role |
| --- | --- | --- |
| `dp` | [https://localhost:8090](https://localhost:8090) | The data plane. Gate and the Admin Console live here. |
| `cp` | [https://localhost:8095](https://localhost:8095) | The control plane and its console. Changes here are applied to `dp` automatically. |
| `auth-dp` | [https://localhost:8091](https://localhost:8091) | A second data plane whose only job is signing operators into the Control Plane Console. |

## Step 1: build and start

This course is built and tested against `main`. The milestone releases trail `main` by hundreds of commits, and several labs fail on them, so build the quickstart pack from source.

You need Git, Go, Node.js LTS and pnpm. The [contributing guide](https://github.com/thunder-id/thunderid/blob/main/CONTRIBUTING.md) lists the exact versions.

1. Clone [thunder-id/thunderid](https://github.com/thunder-id/thunderid) and build the pack:

```bash
git clone https://github.com/thunder-id/thunderid.git
cd thunderid
make build
```

2. Unzip `target/dist/thunderid-<version>-<os>-<arch>.zip` under `target/` and go into the extracted folder. The `thunderid-gateway-*` zip next to it is a lone data plane, not the quickstart.
3. Run `./setup.sh` once. It generates this deployment's TLS, signing and encryption keys, and sets two accounts: `admin` (Control Plane Console) and `servicedeskadmin` (Admin Console). Press Enter to accept a generated password, and note both.
4. Run `./start.sh`.

:::warning[Self-signed certificate]

The local servers use a self-signed TLS certificate, so your browser warns the first time you open each one. Accept the warning for `localhost` on each port. In `curl`, pass `-k`.

:::

## Step 2: tour the consoles

1. Open the Control Plane Console: [https://localhost:8095/console](https://localhost:8095/console). It sends you to `auth-dp` to sign in as `admin`.
2. The console opens in the `Default` project ([module 2](/docs/next/beginner/what-thunderid-is#how-configuration-is-organized)). The sidebar shows what's created inside a project: Applications, Agents, Resource servers, Roles, Flows and Groups under **Build**, and Users and Organization units under **Identities**.
3. Clear the project selection with the ✕ on the **Project** selector in the header. This is the organization-wide view: Projects, Deployment, and the settings **shared by all projects**, such as User types and Connections. Pick `Default` in the selector to go back.
4. Open the Admin Console: [https://localhost:8090/console](https://localhost:8090/console). Sign in as `servicedeskadmin` on the data plane's own Gate.
5. Back in the Control Plane Console, open the `Default` project, then **Users**, and add a user. Pick the bootstrap `Person` user type and the `Default` organization unit. [Module 4](/docs/next/beginner/users-and-user-types) explains user types.
6. A couple of seconds later, find the same user in the Admin Console. That round trip is the control plane applying a new configuration version to the data plane.

A data plane pack ships only the Admin Console. Applications, connections and flows are authored on the control plane, or through a data plane's API and YAML.

## Step 3: peek at the public endpoints

Every OAuth 2.0 and OIDC server publishes what it supports. Open [the discovery document](https://localhost:8090/.well-known/openid-configuration) and [the signing keys](https://localhost:8090/oauth2/jwks) in your browser, or ask from the terminal:

```bash
curl -sk https://localhost:8090/.well-known/openid-configuration | jq
curl -sk https://localhost:8090/oauth2/jwks | jq
```

Skim `grant_types_supported` in the first response. The second one holds the public keys anyone can use to check a ThunderID token's signature.

## Step 4: get a token for the API labs

Later labs call the management API, which needs a token with the `system` permission. The quickest way to get one is from a console you're already signed in to:

1. Open your browser's DevTools and go to the **Network** tab.
2. Click around the Control Plane Console so it makes an API call.
3. Pick any call and copy the bearer token from its `Authorization` header.

```bash
export CP=https://localhost:8095   # where configuration is authored
export DP=https://localhost:8090   # where sign-in runs
export TOKEN=<token from the Control Plane Console>
```

Tokens expire. When calls start returning `401`, copy a fresh one. On a lone data plane, `CP` and `DP` are both [`https://localhost:8090`](https://localhost:8090), and the token comes from its own console.

Do [Set up your environment](https://thunderid.dev/docs/next/use-cases/b2c/build-environment) now. It downloads the Wayfinder sample you'll build out over the next tracks.

Some docs pages were written for a single full Console. Whenever a docs page says to use the Console at `:8090` for applications, flows or import, use the Control Plane Console at `:8095` instead.

## Recap

- Build the quickstart pack from `main`, so the labs match what you run.
- The quickstart pack runs a data plane (`:8090`), a control plane (`:8095`) and `auth-dp` (`:8091`).
- Author on the control plane, inside a project. Watch changes land on the data plane.
- `$TOKEN`, `$CP` and `$DP` are set for every lab that follows.
