:::note[🎯 What you'll do]

- Run ThunderID on your laptop
- Sign in to both consoles and see a change travel from one plane to the other
- Get a token, so the later labs can call the management API

:::

## What you're about to run

The **quickstart pack** runs three ThunderID deployments that are already wired together. You met the two planes in [module 2](/docs/beginner/what-thunderid-is). The third one exists only to sign operators into the control plane.

| Deployment | URL | Role |
| --- | --- | --- |
| `dp` | [https://localhost:8090](https://localhost:8090) | The data plane. Gate and the Admin Console live here. |
| `cp` | [https://localhost:8095](https://localhost:8095) | The control plane and its console. Changes here are applied to `dp` automatically. |
| `auth-dp` | [https://localhost:8091](https://localhost:8091) | A second data plane whose only job is signing operators into the Control Plane Console. |

## Step 1: install and start

Pick one option.

**Option A: the release pack** (anyone)

1. Download `thunderid-2.0.0-m1-<os>-<arch>.zip` from the [v2.0.0-m1 release](https://github.com/thunder-id/thunderid/releases/tag/v2.0.0-m1). The `thunderid-gateway-*` zip is a lone data plane, not the quickstart.
2. Unzip it and run `./setup.sh` once. It generates this deployment's TLS, signing and encryption keys, and asks for two passwords: `admin` (Control Plane Console) and `servicedeskadmin` (Admin Console).
3. Run `./start.sh`.

**Option B: from source** (contributors)

Clone [thunder-id/thunderid](https://github.com/thunder-id/thunderid) and run `make run`. Both accounts default to `admin` / `admin`, and the consoles run on dev servers. [Module 24](/docs/contributor/development-setup) explains the dev setup.

:::warning[Self-signed certificate]

The local servers use a self-signed TLS certificate, so your browser warns the first time you open each one. Accept the warning for `localhost`. In `curl`, pass `-k`.

:::

## Step 2: tour the consoles

1. Open the Control Plane Console: [https://localhost:8095/console](https://localhost:8095/console), or [https://localhost:5193/console](https://localhost:5193/console) from source. It sends you to `auth-dp` to sign in as `admin`. Look around: Applications, Flows, Users, Roles.
2. Open the Admin Console: [https://localhost:8090/console](https://localhost:8090/console), or [https://localhost:5192/console](https://localhost:5192/console) from source. Sign in as the Service Desk Admin on the data plane's own Gate.
3. In the Control Plane Console, create a user. A couple of seconds later, find the same user in the Admin Console. That round trip is the control plane applying a new configuration version to the data plane.

:::tip[On 1.x]

The 1.x releases have no control plane. A data plane there serves one full Console at `/console` that manages everything. On 2.0, every data plane pack ships only the Admin Console, and applications, connections and flows are authored on the control plane or through the data plane's API and YAML.

:::

## Step 3: peek at the public endpoints

Every OAuth 2.0 and OIDC server publishes what it supports. Open [the discovery document](https://localhost:8090/.well-known/openid-configuration) and [the signing keys](https://localhost:8090/oauth2/jwks) in your browser, or ask from the terminal:

```bash
curl -sk https://localhost:8090/.well-known/openid-configuration | jq
curl -sk https://localhost:8090/oauth2/jwks | jq
```

Skim `grant_types_supported` in the first response. The second one holds the public keys anyone can use to check a ThunderID token's signature.

## Step 4: get a token for the API labs

Later labs call the management API, which needs a token with the `system` permission. The quickest way to get one is from a console you're already signed in to:

1. Open your browser's DevTools and go to the **Network** tab.
2. Click around the Control Plane Console so it makes an API call.
3. Pick any call and copy the bearer token from its `Authorization` header.

```bash
export CP=https://localhost:8095   # where configuration is authored
export DP=https://localhost:8090   # where sign-in runs
export TOKEN=<token from the Control Plane Console>
```

Tokens expire. When calls start returning `401`, copy a fresh one. On a lone data plane, `CP` and `DP` are both [`https://localhost:8090`](https://localhost:8090), and the token comes from its own console.

:::info[🧭 Wayfinder step]

Do [Set up your environment](https://thunderid.dev/docs/next/use-cases/b2c/build-environment) now. It downloads the Wayfinder sample you'll build out over the next tracks.

The docs pages were written for a single full Console. On 2.0, whenever a docs page says to use the Console at `:8090` for applications, flows or import, use the Control Plane Console at `:8095` instead.

:::

## Recap

- The quickstart pack runs a data plane (`:8090`), a control plane (`:8095`) and `auth-dp` (`:8091`).
- Author on the control plane. Watch changes land on the data plane.
- `$TOKEN`, `$CP` and `$DP` are set for every lab that follows.
