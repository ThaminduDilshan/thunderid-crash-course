## The idea

ThunderID won't hand tokens to just anyone. An app first has to be **registered**: it gets an identity of its own (a client ID, sometimes a secret) and a set of rules ThunderID enforces on its behalf. Which URLs may people be sent back to? Which ways of getting a token may it use? Which kinds of user may sign in to it?

In OAuth terms, the application is the **client**: it's the one asking for access, on behalf of the person using it.

:::info[🧳 In Wayfinder]

Wayfinder's web frontend runs in the browser, so it's registered as a **browser app**:

- Grant type `authorization_code`, with PKCE required
- Redirect URI: the Wayfinder app's own URL
- Allowed user types: `Customer` only, so staff accounts can't sign in to the customer app

:::

## Application types

The `type` is required and can't change after the app is created. It says what kind of app this is. The OAuth settings decide how it gets tokens, and the console's **templates** (React, Next.js, Android, Wallet and so on) fill those settings in for you. Pick the template closest to your stack.

| Type | For | What the template sets up |
| --- | --- | --- |
| `browser` | Single-page apps: React, Vue, plain JavaScript | Authorization code + PKCE, as a public client |
| `fullstack` | Server-rendered apps: Next.js, Express | Authorization code with a client secret |
| `mobile` | iOS, Android, Flutter | Authorization code + PKCE |
| `m2m` | Backend services with no user | `client_credentials` |
| `mcp` | MCP clients ([module 14](/docs/next/intermediate/mcp-and-delegation)) | Authorization code + refresh |
| `custom` | Anything else, including apps registered through dynamic client registration | Whatever you configure |

The type itself gates one thing: whether the app may run sign-in on its own screens instead of redirecting ([module 11](/docs/next/intermediate/three-ways-to-sign-in)). `browser` and `m2m` apps never can. A `mobile` app needs platform attestation. The other types need the right grants and a Flow Secret.

## What's inside an application

Under the hood an application is an entity of category `app` ([module 4](/docs/next/beginner/users-and-user-types)) with two sets of settings:

- **Sign-in settings:** which flows it runs ([module 6](/docs/next/beginner/flows)), its theme and layout, which user types and agent types may sign in, and which attribute becomes the token's `sub`.
- **OAuth settings:** grant types, redirect URIs, how the client authenticates, PKCE, whether it's public or confidential, token lifetimes and the claims each token carries.

A few rules worth knowing:

- A **public client** (one that can't keep a secret, like a browser app) must use client authentication `none` and PKCE.
- A **client secret** is shown once, in the response that creates the app. Lose it and you regenerate it with `POST /applications/{id}/client-secret/regenerate`.
- The token's `sub` is the user's ID, unless `subjectAttribute` maps a user type to another unique attribute, such as `email`.

## 🧪 Lab: sign in from a React app

Follow the [React quickstart](https://thunderid.dev/docs/next/getting-started/connect-your-application/react). It creates a Vite app, installs `@thunderid/react`, and adds sign-in and sign-out buttons.

A few notes while you follow it:

- Create the application in the **Control Plane Console** ([https://localhost:8095/console](https://localhost:8095/console)), not at `:8090`.
- Point the SDK's `baseUrl` at the **data plane**, [`https://localhost:8090`](https://localhost:8090). That's where sign-in runs.
- The client ID is on the app's **Overview** and **Credentials** tabs, not a General tab.
- Right after you finish, Overview may show no client ID and say the app isn't deployed to `dp` yet. The quickstart pack applies it automatically within a few seconds, so there's nothing to deploy by hand.

Then:

1. Open the browser's DevTools, go to the **Network** tab and turn on **Preserve log**. Sign-in is a full-page redirect, so without it the log is cleared when you leave the app.
2. Sign in. Notice the address bar: you leave your app, sign in on Gate, and come back.
3. In the Network tab, find the `/oauth2/authorize` request, the `/flow/execute` calls Gate makes, and the final `/oauth2/token` call.
4. Copy the ID token from the token response and decode it. Find `sub`, `iss` and `aud`.

:::tip[Also try]

Create an `m2m` app and get a token for it with no user involved:

```bash
curl -sk -u '<client-id>:<client-secret>' -d grant_type=client_credentials $DP/oauth2/token | jq
```

:::

## Recap

- An **application** is a registered client with its own rules.
- The **type** says what kind of app it is. The OAuth settings, prefilled by a template, decide how it gets tokens.
- You've signed a real user in. The rest of the course explains everything that happened in between.
