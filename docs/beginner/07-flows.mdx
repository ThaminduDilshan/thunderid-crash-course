A flow is a stored graph of nodes that ThunderID runs to sign someone in, register them, recover an account and more. Every user journey is a flow, which is why most product behaviour changes without code changes.

## Flow types

| Type | Used for |
| --- | --- |
| `AUTHENTICATION` | Sign-in |
| `REGISTRATION` | Self sign-up |
| `RECOVERY` | Forgot password and other account recovery |
| `SIGNOUT` | Ending an SSO session |
| `USER_ONBOARDING` | An admin onboarding a user |
| `ADMINISTRATION` | Operational flows an admin designs |
| `SELF` <V2 /> | A signed-in user acting on their own account |
| `ADMIN_INITIATED` <V2 /> | Started by an admin, finished by the user |
| `INVITATION` <V2 /> | Inviting a user into an organization unit |
| `DEVICE_GRANT` <V2 /> | The device authorization grant |

There's also `SYSTEM` <V2 />: flows the server runs in process (Ex: before an entity is deleted). No API can create or start one.

## How an application gets its flows

An application points at flows by ID: `authFlowId`, `registrationFlowId`, `recoveryFlowId`, `signOutFlowId` and `deviceGrantFlowId`. Registration and recovery also have an on/off switch. Leave an ID empty and the server fills it from the organization unit's flow for that type, then from the server default (Ex: `default-flow` for sign-in).

## Nodes

| Node | What it does |
| --- | --- |
| `START` / `END` | Entry and exit |
| `PROMPT` | Asks the user for inputs. Carries the UI component tree (`meta`) and the actions the user can take. |
| `TASK_EXECUTION` | Runs an executor (below). Branches with `onSuccess`, `onFailure` and `onIncomplete`. |
| `CALL` | Invokes another flow |
| `VARIABLES` <V2 /> | Declares flow variables, referenced as `{{var(id)}}` |

There's no separate decision node. A flow branches through executor outcomes, prompt actions and node conditions.

## Executors

An executor is one unit of work. Some of the built-ins:

| Purpose | Executors |
| --- | --- |
| Authentication | `CredentialsAuthExecutor`, `PasskeyAuthExecutor`, `MagicLinkExecutor`, `IdentifyingExecutor`, `AuthAssertExecutor` |
| Federation | `GoogleOIDCAuthExecutor`, `GithubOAuthExecutor`, `OIDCAuthExecutor`, `OAuthExecutor`, `OpenID4VPVerifyExecutor` |
| OTP and messages | `OTPExecutor`, `EmailExecutor`, `SMSExecutor` |
| Provisioning | `ProvisioningExecutor`, `AttributeCollector`, `CredentialSetter`, `UserTypeResolver`, `OUExecutor` |
| Authorization and consent | `AuthorizationExecutor`, `PermissionValidator`, `ConsentExecutor` |
| SSO | `SSOCheckExecutor`, `SessionExecutor`, `SessionSignOutExecutor` |
| Integration | `HTTPRequestExecutor`, `ExtensionExecutor` <V2 /> (calls an HTTP connection) |

Some executors are allowed only in some flow types. Ex: the SSO executors only in `AUTHENTICATION`.

## Building flows

The Flow Builder in the console is a drag-and-drop editor over the same JSON. Widgets drop in pre-wired groups of nodes (Ex: User Consent). Flows are versioned: `GET /flows/{id}/versions` and `POST /flows/{id}/restore`.

## 🧪 Lab

1. List the sign-in flows: `curl -sk -H "Authorization: Bearer $TOKEN" "$CP/flows?flowType=AUTHENTICATION" | jq`. Open the default one and find the `PROMPT` node with `action_001`, the `TASK_EXECUTION` node it leads to, and that node's `onSuccess`.
2. Follow [Build a flow](https://thunderid.dev/docs/next/guides/flows/build-a-flow) to make a flow with password, Google and SMS OTP, and assign it to your app.
3. Sign in again through your app and through the [module 9](/docs/intermediate/three-ways-to-sign-in) `curl` loop. Both pick up the new steps with no app change.
