Users, agents and applications are all **entities**: one shared layer with a `category` of `user`, `agent` or `app`. That's why they can all join groups, hold roles and authenticate in similar ways.

| Category | What it is | Its type |
| --- | --- | --- |
| `user` | A person | A user type (Ex: the bootstrap `person`) |
| `agent` | An AI agent or other autonomous software | An agent type (Ex: the bootstrap `default`) |
| `app` | An application ([module 8](/docs/intermediate/applications)) | None. Apps have no schema. |

## Entity types

A user type or agent type is a schema: the attributes an entity of that type has.

- Attribute types: `string`, `email` <V2 />, `mobile` <V2 />, `number`, `boolean`, `object`, `array`.
- Flags on an attribute: `required`, `unique`, `enum`, `regex`, and `credential`. A credential attribute (Ex: `password`) is hashed and stored apart from the profile, and never returned.
- A type can also name its `display` attribute and the primary email and mobile used for notifications.
- Each type belongs to an OU. An OU holds at most one agent type.

The bootstrap `person` type has `username` and `email` (required, unique) and `password` (credential).

**Gotcha:** `unique` is checked across the whole deployment by attribute name and value, not per type or per OU.

## Groups and roles

- A **group** holds members of type `user`, `agent`, `app` or `group`. Members must belong to the group's OU or be shared into it. Nested groups stay in one OU.
- A **role** grants permissions ([module 6](/docs/beginner/authorization)) and is assigned to users, agents, apps or groups. An assignment belongs to one OU, and a group's roles count only in its own OU.

## 🧪 Lab

1. In the console, create a user type `partner` with `username`, `email` and a `password` marked as a credential.
2. Create a user of that type, then `curl -sk "$CP/users/<id>" -H "Authorization: Bearer $TOKEN" | jq`. The password isn't in the response.
3. Create a group, add the user, and assign the group a role.
