## The idea

An AI agent books a trip, files a ticket or calls an API. Who did that? If the agent uses a shared API key or borrows a person's password, nobody can tell afterwards, nobody can limit what it may do, and nobody can switch off just that one agent.

ThunderID gives each agent an identity of its own, managed like a person's: it has attributes, it can join groups and hold roles, and it can be suspended. Its tokens say it's an agent, so an API can treat it accordingly.

:::info[🧳 In Wayfinder]

Wayfinder adds a travel concierge: an AI agent called `WAYFINDER-CONCIERGE` that recommends trips. It's registered as an agent with its own client, and it holds a `Recommender` role that grants `booking:recommend` on the booking API. It can't create or cancel bookings on its own.

:::

## What an agent is

An agent is an entity of category `agent` ([module 4](/docs/next/beginner/users-and-user-types)), shaped by an **agent type** the same way a user is shaped by a user type. The bootstrap agent type is `default`.

- **OAuth client:** an agent can have an OAuth client, so it can get tokens.
- **Owner:** it can record the user or app that owns it.
- **Delegated**: a delegated agent can act for users. A `personal-assistant` agent is owned by one user and acts only for that user.
- **Lifespan**: `validUntil` expires the agent and caps how long its tokens last.

## How an agent signs in

There are four patterns. This module covers the first. [Module 14](/docs/next/intermediate/mcp-and-delegation) covers the rest, once you've seen roles and tokens in more depth.

| Pattern | In plain words | Whose token it is |
| --- | --- | --- |
| **Own token** | The agent signs in with its own client ID and secret (`client_credentials`) | The agent's, with `sub_type=agent` |
| Agent sign-in | The agent completes a sign-in flow, like a person would | The agent's |
| On behalf of a user | A person signs in and agrees to let the agent act for them | The person's, with a note naming the agent |
| Agent to agent | One agent hands part of its authority to another | A chain that records every agent involved |

## 🧪 Lab

1. Create an agent with an OAuth client:

```bash
curl -sk -X POST "$CP/agents" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"default","attributes":{"name":"Sync Bot"},"inboundAuthConfig":[{"type":"oauth2","config":{"tokenEndpointAuthMethod":"client_secret_basic"}}]}'
```

2. Note the client ID and secret in the response. The secret is shown once.
3. Get the agent's own token from the data plane, then decode it and find `sub_type`:

```bash
curl -sk -u '<client-id>:<client-secret>' -d grant_type=client_credentials $DP/oauth2/token | jq
```

## Recap

- AI agents get identities of their own, so their actions are traceable, limited and revocable.
- An **agent** is an entity with an **agent type**, and it can hold roles like a person.
- The simplest pattern: the agent gets its **own token** with `client_credentials`.
