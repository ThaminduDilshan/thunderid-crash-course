ThunderID decides which permissions an access token carries with role-based access control (RBAC). The model has four parts.

- **Resource server:** an API you protect. Its `identifier` (Ex: `https://api.example.com/booking`) becomes the token's `aud`.
- **Resources and actions:** nested inside a resource server. Each one's permission string is its parent's permission, a delimiter (default `:`), then its own handle. A `reservations` resource with a `create` action gives `reservations:create`.
- **Role:** a set of permissions on one or more resource servers, assigned to users, agents, apps or groups.
- **Hierarchical permissions** <V2 />: on a hierarchical resource server, holding a parent permission covers its children.

## How a permission ends up in a token

1. The app asks for scopes and a `resource`. With no `resource`, the configured default resource server is used. With neither, a permission scope fails with `invalid_target`.
2. Requested scopes are cut down to what that resource server defines. Unknown scopes are dropped silently.
3. The flow's Authorization step checks them against the user's role assignments in the OU the sign-in landed in. The default sign-in flow includes this step.
4. The token's `scope` holds only the granted permissions, and its `aud` is the resource server's identifier.

The console itself works this way: the bootstrap **System** resource server has the `system` permission, and the bootstrap Administrator role grants it to the Administrators group.

## AuthZEN

ThunderID is also an [AuthZEN](https://openid.net/wg/authzen/) Policy Decision Point: `POST /access/v1/evaluation` answers "can this subject do this action on this resource" from the same roles. A resource server can instead hand its decisions to an external AuthZEN PDP <V2 />.

## 🧪 Lab

1. Create a resource server with identifier `https://api.example.com/booking`, a resource `reservations` and an action `create`.
2. Create a role with `reservations:create` and assign it to your test user.
3. Sign in through your app with `scope=openid reservations:create` and `resource=https://api.example.com/booking`.
4. Decode the access token and check `scope` and `aud`. Remove the role assignment, sign in again and compare.
